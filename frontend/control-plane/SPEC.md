# Frontend Entry: control-plane

## Purpose

Provide the production FSQ Control Plane browser entry. The entry owns a reusable application shell and left sidebar, a default Overview that separates global AI configuration from Workspace selection and direct Case actions, registry-backed multi-platform workspace navigation and management, a read-only workspace file browser, the workspace-aware Devices page for local execution, and the Config page for managing the single active local model provider.

The entry does not own backend validation, Provider/workspace persistence or authentication protocols, filesystem truth, target/case truth, execution semantics, file editing, or a production implementation of Runs. Workspace selection is in-memory browser state shared by Workspace and Devices; platform selection is always separate and explicit. Ordinary Devices entry does not infer a platform, while the Workspace `Replay Case` command explicitly supplies the platform encoded by the selected case path.

## Dependencies

- React and React DOM provide the component runtime.
- TypeScript is the authored language and type-check boundary.
- Vite and the root Vite React plugin compile the entry within the repository multi-page build.
- Vitest, Testing Library, and a DOM test environment verify focused state and component behavior.
- `ts-ebml` and browser Canvas, `captureStream`, `MediaRecorder`, image, blob, and media APIs provide browser-side seekable WebM replay generation and playback.
- Browser built-ins provide fetch, `AbortController`, `EventSource`, image loading, and accessibility semantics.
- `react-markdown` renders workspace Markdown previews with raw HTML disabled and no raw-HTML plugin.
- `/api/control-plane/*` is the only backend contract consumed by this entry.

The entry must not import Python-generated static assets, backend implementation files, or another frontend entry's private code. It does not introduce Redux, React Query, a client router, Tailwind, CSS-in-JS, or a component framework.

- Optional workspace navigation supplied through typed shell props.
- One bottom Settings destination containing the existing global Provider configuration page; no second settings placeholder or extra settings category page exists.

Feature pages provide active page identity, title-bar context/actions, and outlet content; they do not copy branding, navigation markup, workspace navigation, responsive collapse, or sidebar styles. Runs remains visible but programmatically unavailable with Coming soon, and does not render prototype content or a clickable no-op destination. Settings opens the existing single-Provider management surface with its current layout and workflows. There is no unimplemented Settings entry.

User-visible navigation/page names map to existing internal feature identifiers: Home uses overview, Test Runner uses devices, Workspaces uses workspace, and Settings uses config. Internal feature paths and backend Config transport names are unchanged. Elsewhere in this specification Overview, Devices, and Config refer to those existing implementation owners; their visible page titles and navigation labels use Home, Test Runner, and Settings.

Only the current page destination uses aria-current="page". Workspaces is an expandable navigation group after the primary page destinations. An unavailable registered entry with server-confirmed macOS `diagnosticAvailable` additionally exposes `Check macOS environment`. It opens a transient diagnosis/repair context in Devices without making the unavailable Workspace the application's ready execution selection. In an available Workspace, a configured macOS platform with diagnostic eligibility remains inspectable even when its target is unavailable. Diagnostic context is revalidated against current registry responses and discarded if the registry fails or the entry disappears. It cannot enable Start without fresh shared readiness and target checks.

Activating the Workspaces group header only expands or collapses its entries. It does not navigate, clear or replace Workspace selection, reset platform/Case/Goal state, or trigger draft-discard confirmation. Selecting a specific available Workspace remains the explicit navigation action. Collapse and expand preserve the active page and editing context.

The sidebar is persistent on desktop. At narrow widths the shell owns one accessible collapsed/drawer presentation, keyboard containment while open, close behavior, and focus restoration. Feature pages do not define global navigation breakpoints.

Without a selection it shows the available/partial registered Workspace chooser and one visible Create workspace entry. With a selection it shows a compact identity/action bar and two side-by-side task regions for recording a Case and browsing/replaying existing Cases; the chooser opens on Change Workspace rather than remaining a second permanent list. Buttons keep content width and narrow layouts stack the task regions. Record new case opens Devices Explore with that Workspace and no platform selected; Browse Cases opens its file browser; Configure Workspace selects its configuration presentation. Selection can be cleared without changing persisted Workspace state. These are direct entry actions, not a persistent onboarding checklist. The main region has no unavailable third Run-inspection step and fabricates no Case/Run history.

The independent compact Global AI configuration region shows Provider request/configuration state, safe Provider/model/authenticated summary and Manage Provider. Provider state is not Workspace progress. Overview does not duplicate configuration forms, execution inputs, preflight or evidence.

The global Provider region states that configuration comes from `~/.fsq` and is shared by every Workspace, and it navigates to Settings (the `config` feature) for management. The application obtains Provider configuration through the existing Config API and projects only a safe Overview summary: request state, configured/unconfigured state, the explicit OpenAI/Azure OpenAI/Google Gemini/GitHub Copilot identity, model name, and GitHub authenticated state when applicable. The complete Config response, Azure endpoint, OpenAI/Azure/Gemini API keys, token values, authentication material, raw exception detail, and unrestricted response content do not enter Overview props or state and are never rendered there. Provider loading, configured, unconfigured, and unavailable/error states remain distinct; errors expose only the API contract's safe message and action. Provider state is not counted as current-Workspace progress.

The current-Workspace region strongly identifies the selected Workspace by registry name and safe configured-platform labels/status only. It never displays an absolute root/configuration path, private target value, environment value, or device identity. An available or partial registry entry may establish current Workspace identity; the user can explicitly clear that Overview selection and return to the available-Workspace chooser without deleting or modifying any Workspace. At least one platform with `status=available` is required before Workspace-dependent Devices actions are enabled. A selected Workspace with only unavailable platforms remains identified but is directed to Workspace for repair. Workspace creation includes at least one platform, so creation and first-platform setup form one step. There is no separate readiness step: Devices owns readiness and performs preflight before execution.

Workspace actions derive from authoritative registry/platform truth. Record requires an available/partial Workspace with at least one available platform; missing/unavailable platforms expose a nearby repair explanation. Browse and Configure retain Workspace eligibility. Record never infers a default platform. Case completion, Run inventory, Doctor results, readiness and evidence completion are not fabricated or persisted as Overview truth. Runs remains unavailable in navigation with a truthful Coming soon label.

The application owns Workspace registry loading/ready/error state and the single validated selected Workspace used by Shell, Overview, Workspace, Devices, Record, and Replay. A failed registry request invalidates ready registry truth for every consumer; stale entries or selection may not remain actionable or identify a current ready Workspace. After a successful refresh, a selected entry that disappeared or became unavailable is likewise revoked before consumers render. Retry establishes new authoritative registry truth. Overview issues no direct registry, Config, filesystem, readiness, Case, or Run request.

The page uses the shared light visual system, flat neutral background, white surfaces, fine borders, restrained indigo accent, Workspace navigation, title bar, and responsive drawer behavior. It uses one normal page layout without simulating another sidebar, semantic regions and direct-action structure, visible focus, truthful disabled explanations, and responsive layouts without page-level clipping. Loading, empty, error, and retry states are explicit and accessible.

### Workspace navigation and creation

The application loads `/workspaces` as shared truth and distinguishes registry loading, empty, partial/unavailable, error, and retry before supplying validated Workspace identity to the Workspace feature. `Create workspace` initially shows workspace name, a read-only selected-folder field with a `Choose folder` action, and a read-only `Final path` field. Before selection the final path is empty. After selection it equals the selected folder when trusted-local `isEmpty=true`, or `<selected-folder>/<workspace-name>` when `isEmpty=false`; changing the name recomputes only the non-empty-folder preview. It has no implicit platform draft. Each `Add platform` action appends one complete platform section vertically below the workspace identity fields, containing platform selection, platform-specific target controls, and a collapsed-by-default optional Environment disclosure. A Web target presents a required browser-channel selector containing every supported Chromium distribution channel together with an optional executable path. When omitted, supporting text states that FSQ discovers the selected installed channel; the request omits the field rather than sending an empty string.

`Choose folder` calls the trusted-local `POST /workspaces/pick-parent-directory` transport and never accepts manual path entry. While selection is pending, duplicate selection and workspace submission are disabled without clearing other drafts. A selected response replaces the transient selected path and trusted `isEmpty` fact and updates the final-path preview; cancellation preserves both prior values and restores focus to the action; failure preserves every draft and exposes a retryable scoped error without a manual-entry fallback. Stale responses after form abandonment do not repopulate state. Workspace creation submits `selectedPath` with the independent workspace name and complete platform drafts; the preview is presentation only and is not submitted as root authority.

Target controls follow backend discriminator rules: Android requires App ID; Web requires Browser channel and accepts an optional Browser executable path; Windows requires App path and optionally accepts Window title regex and Launch args; macOS accepts Bundle ID and App path with at least one required. The same Web optional-path contract applies to create, add, and edit. A draft may change platform before submission and clears its old target/env values. Every platform dropdown keeps all supported values visible but disables values selected by another draft, so one create request cannot contain duplicate platforms. Unsaved platform sections may be removed, including the final section, returning the form to its initial identity-only state. Environment rows use validated name controls, password value controls, add/delete actions, and per-value eye-icon show/hide buttons with tooltips and accessible state labels.

Client validation improves feedback but server validation remains authoritative. Submit validates workspace name, selected folder, at least one platform section, and every platform draft in that order; failure focuses the first missing or invalid control. Pending creation locks competing controls, directory selection, and duplicate submission. Server conflicts/path errors preserve every draft. Cancel clears all target/env and selected-folder drafts and restores focus to the initiating control. Successful creation refreshes registry truth, selects the new workspace, opens its main Workspace page, and focuses the workspace heading.

### Config

The Config feature uses the shared shell and visible page title Settings. It retains the existing Provider page layout, forms, authorization, model selection, and connection checks without adding empty settings categories. Entry loads the local Config API and distinguishes loading, unconfigured, configured OpenAI, configured Azure, configured Google Gemini, configured GitHub, unavailable, and error states. Unconfigured state has one `Add configuration` action. Configured state has `Change provider`; the application never presents retained profiles or a Switch provider action. Internal `config`, `overview`, and `devices` page ids, component ownership, and API paths are unchanged; their visible destinations remain Settings, Home, and Test Runner.

Add/Change opens an accessible provider-choice dialog containing OpenAI, Azure OpenAI, Google Gemini, and GitHub Copilot in that order. OpenAI is the first available focus target. Selecting OpenAI, Azure, or Gemini closes the dialog and shows its configuration form in the main outlet; selecting GitHub immediately requests device authentication with no model field. Choosing the current provider is allowed as a replacement flow. The saved provider remains active until a complete candidate is activated. API-key form titles and all Provider summaries identify the concrete service, not a shared GPT-with-Azure-toggle type. Choice cards stack on narrow screens and use the shared visual/control tokens and `DialogFrame` behavior.

The OpenAI form contains a required API key, an explicit `Load models` command, and a native Model select populated only from backend-offered eligible models. No endpoint input, unrestricted model-name input, automatic page-load discovery, or default model is present. The saved key is populated from the trusted-local Config representation, masked by default, and explicitly revealable. Discovery state is idle, loading, ready, empty, or error with retry. A valid empty response is an explicit unsaveable state rather than a generic error. Authentication, permissions, quota/rate-limit, timeout/network, and malformed-response failures retain safe operation-specific guidance without exposing upstream data.

A new OpenAI draft starts without a selected model. Editing a saved OpenAI Provider shows its current model/key; loading is required before selecting another model. Reloading the same saved key may retain its saved model only if that exact id remains offered; it never selects a different default. Changing the key clears the candidate list and selection and requires another load and explicit selection. Key changes, Provider changes, navigation, or unmount abort outstanding discovery and invalidate its request generation so late results cannot repopulate another draft. Loading disables duplicate discovery and saving. Save requires a normalized dirty complete draft, a selection from the current list, and no pending discovery/save or blocked reconciliation; backend selection validation remains authoritative.

Google Gemini uses the `google_gemini` discriminator and a separate `GoogleGeminiConfigForm` with required API key, explicit `Load models`, native Model select, Cancel, and Save. It uses the same candidate-key, no-default-selection, key visibility, dirty state, stale-request invalidation, and Save eligibility rules as OpenAI, but keeps supplier-specific drafts and request generations separate. The client calls the documented `/config/google-gemini/models` and `/config/google-gemini` transports and accepts only their exact validated response shapes. It offers only the complete backend-provided list of stable Gemini 3-or-later general-purpose Flash/Pro models, preserving backend order; it does not implement model-version filtering or Google pagination. Empty discovery is explicitly unsaveable, and incomplete discovery is a scoped error without an actionable partial list. A same-key reload may preserve the saved model only if it remains offered; newly discovered models are never selected automatically.

Gemini configuration exposes no endpoint, free-text model, Vertex AI, cloud project, service account, or advanced generation settings. It never calls Google from the browser. On save, Application revalidates the offered model before persistence; the frontend applies only returned or freshly reconciled Config truth. Settings and connection results name Google Gemini explicitly, and Home receives only its safe identity/model projection. Test Runner consumes Gemini through existing Provider readiness and frozen-run contracts; it has no Gemini-specific execution mode or alternate readiness calculation.

The Azure form contains required Base URL, Model name, and API key fields. Model guidance recommends GPT 5 or later without restricting other non-empty names. API key is populated from the trusted local response, masked by default, and has an eye-icon control with accessible show/hide labels and tooltip. Save submits the complete form and disables competing controls while pending. Cancel returns to the unchanged empty/configured presentation. Dirty state is derived from normalized loaded and draft values; navigating to Devices, starting Change provider, or cancelling while dirty requests discard confirmation. Browser refresh discards the draft.

OpenAI, Azure, and Gemini drafts are separate from saved Provider truth. Dirty comparison trims surrounding whitespace; model-discovery state alone is not dirty. Cancel or confirmed discard before save submission clears candidate values, discovery state, and secret reveal state and restores the saved presentation. Replacement drafts never borrow another Provider's key. Discard prompts identify unsaved Provider changes rather than assuming Azure. Fields, secret controls, Cancel/primary action ordering, modal spacing, responsive behavior, and focus treatments use the shared light-neutral/indigo visual system; Settings does not introduce a grid background or competing control styles.

OpenAI and Gemini saving expose a secret-free busy flag to the application navigation guard. While pending, field edits, discovery, duplicate submission, Cancel, Change provider, and Test connection are disabled, and application-controlled page/Workspace navigation cannot discard the form. Browser reload, tab closure, process exit, or network loss are not cancellable-save guarantees. A successful response applies returned Config truth and clears the submitted draft. A known pre-commit rejection or confirmed storage rollback preserves the old saved snapshot and retryable candidate.

A disconnected/aborted save, unreadable success response, or ambiguous internal failure enters an explicit unknown-outcome state, not an ordinary failed save. The candidate remains separate and is not automatically resubmitted or rolled back. While mounted, the feature performs one fresh Config read and exposes `Reload configuration` for explicit retry. Without a valid read, saved truth is unavailable and mutations/testing remain blocked. A successful read establishes the current snapshot and a reconciled state; explicit actions resume under normal dirty/replacement/test eligibility while a notice retains that the original request outcome was not confirmed. Matching candidate values are not proof of that request's success, and an old snapshot is not proof that a delayed save cannot commit later. Navigation during unresolved recovery requires a warning that leaving does not cancel the save. Re-entry and later reconciliation read current server truth; stale save callbacks cannot overwrite it. No server transaction-status, idempotency, cancellation, or concurrent-save ordering protocol is implied.

GitHub waiting state displays the verification URI as a new-tab link, user code with a copy control, expiration, status, and Cancel. The feature polls waiting and post-authorization model-loading states at bounded server-provided intervals. Authorization success leads to authenticated model discovery rather than immediate persistence. Discovery success presents a required native Model select containing only the backend-offered general-purpose GPT 5-or-later models in service order; it starts with no selected value, and Save is disabled until the user explicitly selects one. Save submits the selected model for the same pending authorization and closes the dialog, refreshes Config, restores focus, and displays authenticated provider/model state only after persisted Config truth is returned.

Device-code failure, denial, and expiration retain a safe Retry that starts a new authorization. Model-discovery failure retains the pending authorization and offers Retry models; an empty eligible list is explicit, retryable, and cannot be saved. Save failure preserves the selected model and previous provider for retry while the transaction remains valid. Close, cancellation, navigation, unmount, pending-transaction expiration, or backend shutdown clears unsaved GitHub state and preserves the previous provider. Polling, timers, and stale requests are cleared on every terminal or abandoned transition.

After a provider is persisted, the bottom action area contains `Test connection`. It tests only the latest saved configuration and is enabled only with a valid saved snapshot, no unsaved OpenAI/Azure/Gemini edits or replacement draft, and no discovery, save, device-flow transition, test, or blocked reconciliation pending. Success and failure use a result dialog; success shows the explicit Provider identity, model, and elapsed duration, while failure shows the backend message/action without changing saved configuration. A successful minimal connection test is not proof that every model feature or Case works. The feature captures the initiating element before it becomes disabled, supplies `DialogFrame.returnFocus`, and restores focus to that connected control on dismissal. Async dialog content changes retain modal focus and Tab containment.

Config API unavailable state explains that editable configuration requires a loopback-bound and loopback-accessed Control Plane and does not expose editable values. Long endpoints, models, codes, and errors wrap without horizontal overflow.

### Devices context and discovery

The Devices-owned page context region contains, in order:

- Workspace selection sharing the application's in-memory selected workspace.
- Explicit platform selection containing only valid configured platforms for that workspace; ordinary Devices entry selects no platform implicitly, including when only one is valid, while `Replay Case` is an explicit request to initialize the path-derived platform when it remains available.
- Platform-specific target selection labelled Device, Browser, or Application.
- Text-plus-icon connection/readiness status and Refresh.

While idle, changing workspace or platform aborts outstanding readiness/target/case requests, clears every downstream value tied to the prior context, and starts a new request generation. Workspace changes do not infer a platform from the available configured-platform set; downstream discovery waits until both workspace and platform selection exist. Once both selections exist, readiness, targets, and cases may load independently; readiness responses apply only when their full selection context still matches. Android additionally binds readiness to the selected device, as defined below. Refresh reloads the same context without creating a run.

Workspace case actions reach Devices through one transient mounted-application launch intent rather than a route, browser storage, or backend contract. Each activation has a fresh identity and is consumed once. An Explore intent carries the current workspace and opens Explore without a platform. A Strict intent carries the current workspace, path-derived platform, and relative case path and opens Strict Replay. Bootstrap restoration of an active task takes precedence over either intent. Without an active task, Devices accepts the offered workspace and platform only while they remain selectable, then accepts the case only when current discovery returns the exact relative path with `selectable=true`. A missing or unavailable platform is left unselected; a missing or non-selectable case leaves Strict Replay active with no case selected and Start disabled by existing eligibility rules. Normal Devices navigation has no launch intent and retains its existing selection behavior.

During `preparing`, `running`, and `finalizing`, workspace, platform, and target controls are locked to the frozen run context. New run preserves the last explicit workspace/platform selection when still present but must re-establish current readiness before start.

Activating Jump to latest synchronously sets the corresponding scroll region to its actual maximum scroll position, verifies bottom-follow state from the resulting geometry, clears the unseen count, removes the control, and transfers keyboard focus to that scroll region rather than leaving focus on a removed element. Returning to the bottom through ordinary scrolling also resumes following. Terminal runs never display Jump to latest regardless of preserved scroll position or focus. Run connection/update state is not rendered as a separate row beneath the source summary; timeline rows keep a small stable gap below the source summary. The timeline scroll region shows its vertical scrollbar from initial render without horizontal scrolling, so timeline cards remain visually centered and do not shift when scrolling becomes necessary.

The frontend does not fabricate waiting/completed timeline steps. Live updates do not steal focus.

Draft status comes from backend `recordingDraft` and is identified in the save dialog and result without embedding Run metadata in Case YAML. The editable filename text and path preview use normal text weight rather than bold emphasis. ### Live evidence

The right panel exposes semantic Screen, UI Tree, and Logs tabs:

- Screen shows the latest real screenshot while a run is active. After completion with no selected Action, it automatically resolves or generates the persisted run replay and displays the stored seekable WebM with native playback controls. With an Action selected, it displays that step's available Before and After screenshots as a centered side-by-side comparison in capture order; one-sided evidence is shown without an empty fabricated counterpart. Selected Action screenshots are displayed as the original captured image content without additional image rounding, surrounding device-frame styling, or altered screenshot pixels. Selected Action screenshot media uses nearly the same visible sizing envelope as the run replay video: it should grow to use the available evidence-surface height and width, especially for Android portrait captures, while preserving comparison order, `object-fit: contain`, and internal scrolling instead of page-level clipping. Wide selected-Action screenshots are constrained by the visible evidence-surface width so a two-image Before/After comparison does not force page-level or evidence-surface horizontal scrolling; when two wide screenshots cannot fit side by side within the visible surface, the comparison stacks in capture order instead of stretching the images past the surface. Each selected Action screenshot keeps a compact white header directly attached above the image with dark Before/After text, matching the rendered screenshot image width rather than stretching across the grid column, so the label stays visually attached to the image.
- Screen evidence surfaces use a subtle grid workbench background behind screenshot, selected-Action screenshot, replay-video, and replay-generation states. Screenshot and replay-video media use the same visual sizing envelope and are constrained to the visible evidence surface with `object-fit: contain` behavior so desktop and narrow viewports can inspect the whole media without page-level clipping; overflow stays inside the evidence surface when the available viewport is smaller than the media.
- UI Tree loads the latest normalized `ui_snapshot` while a run is active. With a terminal Action selected, it displays the available Before and After normalized snapshots as a read-only full-content diff with line-level and paired inline change highlighting; one-sided evidence remains readable and is not treated as a failed run. When a UI snapshot contains XML, the UI Tree view parses it into a readable structured tree that preserves useful element names, text-like attributes, state, and geometry signals, and falls back to raw text when XML parsing fails.
- Logs render structured time, level, phase, tool, status, and safe message rows rather than raw JSON. The message column is width-bounded and defaults to a single-line ellipsis view that cannot widen the table; activating the message disclosure shows the complete message. The message column starts narrower than before and can be resized horizontally through a drag handle in the Logs header, with the width stored only in component state. Each log row exposes a native disclosure control that expands a complete pretty-printed safe JSON view of the event fields returned by the backend, including optional fields such as `sequence`, `stepId`, `label`, `durationMs`, `payload`, `toolCallId`, `toolArguments`, and `toolOutputPreview` when present. The Details JSON region never widens the table; it has its own horizontal scroll for long fields. The table header remains sticky in the bounded Logs scroll region. Logs do not expose Jump to latest; users inspect history through the Logs scroll region.

Replay generation is automatic after terminal completion. The browser requests persisted screenshot frames in chronological order, uses their timestamps to derive bounded display durations, renders them through Canvas and `MediaRecorder`, converts the result to a seekable WebM through `ts-ebml`, uploads it to the frozen run, and then plays only the stored range-capable video URL. An existing stored video is reused. Runs with no readable frames show an unavailable state; unsupported browser media APIs, frame failures, generation failures, upload failures, and playback failures stay local to Screen and never change the truthful run result. Object URLs, media streams, timers, and in-flight generation are cleaned up when the run, selection, or component changes.

Each tab distinguishes loading, not-yet-captured, unavailable, oversized, failed, and available states. Evidence-tab failures do not replace the run result.

The run stream resumes from the last accepted sequence. On stream failure, the client reconnects with bounded backoff and then falls back to run snapshots. A browser reload uses bootstrap to discover and resubscribe to a live in-memory request.

## Frontend Architecture

- Architecture level: Level 3 Layered Frontend Application.
- Runtime boundary: React/TypeScript in the browser, consuming only `/api/control-plane/*`.

- Rationale: the entry separates an application shell, independent Workspace/Devices/Config workflows, explicit transport validation, and complex server/transient state; no router, global store, or additional data layer is required.

## Error Handling

The API client recognizes structured `code`, `message`, `action`, and optional safe `details`. User-visible errors say what happened and what action is available. They do not display tracebacks, hidden reasoning, raw internal JSON, secret values, or unnecessary local paths.

Workspace or platform changes cancel stale requests and clear downstream state. Target/case/config disappearance or revision change at run start is shown as authoritative server validation failure and triggers relevant refresh guidance. Stream disconnection is shown as reconnecting without changing task outcome. Screen/UI-snapshot, selected-step artifact, replay-frame, video-generation, upload, and playback failures stay scoped to their evidence surface. Selected-step artifact loading preserves any already rendered selected-Action evidence until the newly selected Action resolves or fails. A restarted backend reports that the prior live session ended rather than presenting a stale running state.

Workspace registry failure revokes authoritative ready registry truth and the validated current Workspace for every application consumer; stale registry content is not selectable, actionable, or presented as current ready identity. Selected-Workspace summary/platform-detail failures may preserve last safe feature truth only when identified as stale and visibly unavailable; they do not synthesize empty success. Parent-folder picker cancellation is a successful no-change outcome; picker failure preserves the prior selection and all other create drafts, remains scoped to the picker control, and offers retry without text-entry fallback. Create/add failures preserve all draft values and clear them only on explicit cancel/confirmed navigation/success. Update failures preserve loaded disk truth and the selected platform's unsaved draft separately. A revision conflict offers Reload latest and never silently resubmits. Directory/file failures remain scoped to the selected node/content pane. Frontend errors and diagnostics never include env values, secrets, or unrestricted response bodies.

Empty states direct the user to create/select a workspace, add a configured platform, add a Provider, select a Devices platform when multiple valid choices exist, connect a target, provide a goal, or add a valid case. Missing files/evidence are not represented by blank success panels. Workspace and Config failures remain scoped to their features and never fabricate persisted state.
